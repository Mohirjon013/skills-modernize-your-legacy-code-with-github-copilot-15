# COBOL Student Account Test Plan

This test plan validates the current COBOL account-management business logic and implementation. It is structured so that each case can later be implemented as a unit or integration test in Node.js. `Not Run` is used as the initial status until stakeholder or QA validation is performed.

| Test Case ID | Test Case Description | Pre-conditions | Test Steps | Expected Result | Actual Result | Status (Pass/Fail) | Comments |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TC-001 | Application starts and displays the account menu | Application is started from a clean process; no previous account state is in memory | 1. Start the COBOL application.<br>2. Observe the menu. | The application displays the separator, `Account Management System`, options `1. View Balance`, `2. Credit Account`, `3. Debit Account`, `4. Exit`, and prompts for a choice from 1-4. | | Not Run | Maps to `MainProgram` menu initialization and repeat loop. |
| TC-002 | Initial balance is available | Application has just started; no credit or debit has been processed | 1. Start the application.<br>2. Select menu option `1`. | `DataProgram` reads the initial stored balance and the application displays `Current balance: 1000.00` (formatting may reflect COBOL PIC formatting). | | Not Run | Baseline account balance. |
| TC-003 | View balance reads the stored value | The account has a known balance established through a successful credit or debit | 1. Establish a known balance.<br>2. Select menu option `1`. | The application displays the same known balance that is stored by `DataProgram`; no balance change occurs. | | Not Run | Validate the `TOTAL ` operation and `READ` path. |
| TC-004 | Credit account increases the balance | Application starts with a clean balance of `1000.00` | 1. Select menu option `2`.<br>2. Enter a valid credit amount, for example `250.00`.<br>3. Confirm the application result. | The application reads `1000.00`, adds `250.00`, writes `1250.00`, and displays `Amount credited. New balance: 1250.00`. | | Not Run | Unit test: credit calculation; integration test: `Operations` to `DataProgram` write. |
| TC-005 | Multiple credits accumulate correctly | Start with the initial balance and no prior changes | 1. Credit `100.00`.<br>2. View the balance.<br>3. Credit `50.25`.<br>4. View the balance. | The first view shows `1100.00`; the second credit updates the stored balance to `1150.25`; the final view shows `1150.25`. | | Not Run | Verifies persistence in `STORAGE-BALANCE` for multiple operations. |
| TC-006 | Credit with zero amount leaves the balance unchanged | Application starts with a clean balance of `1000.00` | 1. Select menu option `2`.<br>2. Enter `0.00`.<br>3. View the balance. | The application reports a new balance of `1000.00`, and the stored balance remains `1000.00`. | | Not Run | Zero is valid according to the numeric COBOL field, although it is not defined as a business-positive-credit rule. |
| TC-007 | Debit below the available balance succeeds | Application starts with a clean balance of `1000.00` | 1. Select menu option `3`.<br>2. Enter `400.00`.<br>3. Confirm the application result. | The application reads `1000.00`, verifies sufficient funds, subtracts `400.00`, writes `600.00`, and displays `Amount debited. New balance: 600.00`. | | Not Run | Unit test: debit calculation; integration test: `Operations` to `DataProgram` write. |
| TC-008 | Debit equal to the available balance succeeds | The account balance is `1000.00` | 1. Select menu option `3`.<br>2. Enter `1000.00`. | The debit is accepted because `balance >= amount`; the application writes `0.00` and displays `Amount debited. New balance: 0.00`. | | Not Run | Boundary case: equality is allowed. |
| TC-009 | Debit greater than the available balance is rejected | The account balance is `1000.00` | 1. Select menu option `3`.<br>2. Enter `1000.01`. | The application displays `Insufficient funds for this debit.` and does not execute a `WRITE` operation; the stored balance remains `1000.00`. | | Not Run | Core insufficient-funds business rule. |
| TC-010 | Insufficient-funds debit leaves later operations unchanged | An insufficient-funds debit has just been attempted | 1. Attempt to debit `1000.01` from a `1000.00` balance.<br>2. View the balance.<br>3. Credit `50.00`.<br>4. View the balance. | The failed debit does not alter the balance; the view shows `1000.00`; after the credit, the view shows `1050.00`. | | Not Run | Ensures failed operations have no side effects and later operations use the correct stored state. |
| TC-011 | Multiple debits enforce the running stored balance | Application starts with a clean balance of `1000.00` | 1. Debit `600.00` successfully.<br>2. View the balance.<br>3. Debit `400.00` successfully.<br>4. View the balance. | The first view shows `400.00`; the second debit results in `0.00`; the final view shows `0.00`. | | Not Run | Verifies the balance is read and updated for every debit. |
| TC-012 | Debit from a zero balance is rejected | The account balance is `0.00` | 1. Select menu option `3`.<br>2. Enter a positive amount, for example `0.01`. | The application displays `Insufficient funds for this debit.` and keeps the balance at `0.00`. | | Not Run | Boundary case for a depleted account. |
| TC-013 | Credit followed by debit uses the updated balance | Application starts with a clean balance of `1000.00` | 1. Credit `200.00`.<br>2. Debit `150.00`.<br>3. View the balance. | The account is updated to `1200.00` after the credit and `1050.00` after the debit; viewing it shows `1050.00`. | | Not Run | Integration test across consecutive `READ`, `ADD`, `WRITE`, `READ`, and `SUBTRACT` operations. |
| TC-014 | Invalid numeric menu choice is rejected | The application is running at the menu | 1. Enter menu choice `5`.<br>2. Observe the result.<br>3. Enter a valid menu choice `4` to exit. | The application displays `Invalid choice, please select 1-4.` and remains in the menu loop; it exits successfully only after `4` is entered. | | Not Run | Covers the `WHEN OTHER` branch and loop continuation. |
| TC-015 | Non-numeric or unsupported menu input is handled safely | The application is running at the menu | 1. Enter an unsupported non-numeric value at the menu prompt.<br>2. Observe the result.<br>3. Enter `4` to exit. | The application does not execute a valid account operation and does not terminate unexpectedly; if COBOL PIC 9 handling maps the input to an invalid value, it follows the invalid-choice branch and remains usable. Stakeholders should confirm exact behavior for runtime-specific input handling. | | Not Run | COBOL runtime input coercion is platform-dependent; document the exact Node.js validation behavior before implementation. |
| TC-016 | Exit option terminates the application loop | The application is running at the menu | 1. Enter menu choice `4`. | `CONTINUE-FLAG` becomes `NO`, the menu loop ends, and the application displays `Exiting the program. Goodbye!` before stopping. | | Not Run | Covers the normal exit path. |
| TC-017 | Restart restores the initial account balance | A prior run has changed the account balance | 1. Change the balance by a successful credit or debit.<br>2. Exit the application.<br>3. Restart the application.<br>4. Select menu option `1`. | The new process displays the initial stored balance `1000.00`; no balance change is persisted to disk or an external store. | | Not Run | Documents the implementation's in-memory `STORAGE-BALANCE` behavior. |
| TC-018 | Credit decimal precision is preserved | Application starts with a clean balance of `1000.00` | 1. Credit `123.45`.<br>2. View the balance. | The amount is handled as two-decimal currency and the result is `1123.45`, with no loss of cents. | | Not Run | COBOL amount field: `9(6)V99`; Node.js implementation should use integer cents or a decimal-safe strategy. |
| TC-019 | Debit decimal precision is preserved | The account balance is `1123.45` | 1. Debit `23.45`.<br>2. View the balance. | The application calculates and writes `1100.00`, preserving two-decimal precision. | | Not Run | Node.js implementation should avoid floating-point rounding errors. |
| TC-020 | Large valid credit does not silently lose precision or exceed the field | Application starts with a clean balance of `1000.00` | 1. Attempt a credit near or above the COBOL field limit.<br>2. Observe the resulting balance and runtime behavior. | Stakeholders must approve overflow behavior. The COBOL field supports a maximum of `999999.99`; the implementation must not silently wrap or truncate. A clear validation or overflow response is preferred when migrating to Node.js. | | Not Run | Migration requirements case: current COBOL does not include an `ON SIZE ERROR` overflow branch. |
| TC-021 | Data store READ operation returns the current balance | `STORAGE-BALANCE` contains a known value | 1. Invoke the data operation with `READ` and a supplied balance variable.<br>2. Inspect the returned balance. | `STORAGE-BALANCE` is copied into the supplied balance and the result equals the stored value. | | Not Run | Direct unit test for `DataProgram` READ behavior. |
| TC-022 | Data store WRITE operation updates the current balance | `STORAGE-BALANCE` contains a known value and a new balance is supplied | 1. Invoke the data operation with `WRITE` and the new balance.<br>2. Invoke `READ` and inspect the balance. | The supplied balance is copied into `STORAGE-BALANCE`; subsequent READ operations return the new balance. | | Not Run | Direct unit test for `DataProgram` WRITE behavior. |
